Why routing

Step 1/Single screen

The limits of a single screen

Our app always shows the same screen. To add a login page with what you know today, you'd need a piece of state and a conditional:

const [showLogin, setShowLogin] = useState(false);

return showLogin ? <LoginForm /> : <ProfessionalsList />;
  • That works for two screens. Now add a register page: you need a second flag, and both can be true at the same time. Which screen shows?
  • The address bar never changes either. Back does nothing, refreshing sends you to the start, and you can't send anyone a link to a screen.

Ask the room how they'd add a login screen with what they know today. Someone will say a boolean and a ternary. That's the right answer with the tools they have, and it's exactly the thing that doesn't scale.

Step 1/The idea

Nothing here is a new page load. It's still one React app with one index.html — a router just picks which component to render for the current address.

The phrase worth landing: the URL is a piece of state that lives in the address bar instead of in useState. Back, forward, refresh and bookmarks are all free once that's true.

The core API

Step 03

Context

A value the whole app can read, without passing it down.

Around twenty minutes, led. Do not skip the prop-drilling slide — without the problem, context is magic.

Step 3/Prop drilling

The prop drilling problem

Two things already need to know who's logged in: the nav bar, to show "Log out", and the login page, which is what sets it. With props alone, the token has to live in App and be handed to both:

function App() {
  const [token, setToken] = useState(null);   // App never uses this itself

  return (
    <>
      <NavBar token={token} />

      <Routes>
        <Route path="/" element={<ProfessionalsPage />} />
        <Route path="/login"
               element={<LoginPage setToken={setToken} />} />
      </Routes>
    </>
  );
}

That's prop drilling. App is storing something it never reads, just so it can pass it on — and every new screen that needs the token means editing App again. In Step 6 you'll add one more thing that needs it.

Don't write this code — show it and move on. It's the "before" picture, and the next slides replace it.

Be fair to props: passing a value to your own child is normal and stays normal. Context is for the handful of values the whole app needs.

Step 3/What it is

How Context works

PartJob
createContext()Makes the container. Once, at the top of the file.
<Context.Provider value={…}>Supplies the value. Everything it wraps can read it.
useContext(Context)Reads the value, from any depth, with no props involved.

Context is a delivery mechanism, not a storage mechanism. The value still lives in ordinary useState — context only changes who can reach it.

That last line is the one to repeat. Students consistently believe context replaces state; it replaces props.

Step 3/localStorage

localStorage

Every piece of React state is wiped on refresh. localStorage is a small key/value store built into the browser that isn't — which is where the token has to live if a logged-in user is going to stay logged in.

localStorage.setItem("token", "eyJhbGciOi…");   // save it
localStorage.getItem("token");                  // read it back — null if there isn't one
localStorage.removeItem("token");               // delete it
  • Strings only. Anything else has to go through JSON.stringify on the way in and JSON.parse on the way out. A token is already a string, so we're fine.
  • It survives everything — refresh, closing the tab, restarting the machine — until your code deletes it or the user clears their browser data.
  • One store per origin. What localhost:5173 saves, no other site can read.

Open DevTools → Application → Local Storage and show the empty table now. Coming back to it after the login step, with a real token sitting in it, lands better than any slide.

If someone asks whether it's secure: it is not a secret store — any script running on your page can read it. Acknowledge it and move on. It's a real topic, and not today's.

Step 3/The file

Fill in context/AuthContext.jsx

import { createContext, useContext, useState } from "react";

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [token, setToken] = useState(() => localStorage.getItem("token"));

  function login(newToken) {
    localStorage.setItem("token", newToken);
    setToken(newToken);
  }

  function logout() {
    localStorage.removeItem("token");
    setToken(null);
  }

  const value = { token, isLoggedIn: token !== null, login, logout };

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth() {
  return useContext(AuthContext);
}

The placeholder already has the imports, the createContext line and useAuth. What they add is the body of AuthProvider — type that out rather than pasting it. It's the densest code of the session and every line earns a sentence; the slides that follow are the sentences.

If someone asks why setItem isn't in a useEffect watching token — because it would also fire on first load with the value it just read, and write the string "null" on logout unless you guard it. Saving happens because someone logged in, and login() already runs at exactly that moment. Answer it only if asked; don't raise it yourself.

Expect a red squiggle. ESLint says "Fast refresh only works when a file only exports components", because this file exports a component and a hook. It's a hot-reload preference, not a bug — your placeholder file already carries an eslint-disable comment at the top with that explanation, so leave it there. Keeping the context, its provider and its hook together is the normal convention.

Step 3/Details

Four details to note

  • children is a prop like any other. Whatever you nest inside <AuthProvider>…</AuthProvider> arrives as children.
  • useState(() => localStorage.getItem("token")) — why the arrow? JavaScript evaluates an argument straight away, so without it localStorage is read on every render and the result thrown away after the first. Wrapped in a function, nothing is read until React calls it — which it does once, on the first render, and never again.
  • isLoggedIn is derived, not stored. Two pieces of state that must agree eventually won't.
  • useAuth is a custom hook — and a custom hook is nothing but a function that calls other hooks. It saves every component importing the context object separately.

The lazy initializer catches everyone. Show what happens without the arrow by adding a console.log inside it — a wall of logs.

"Derived, not stored" is the same rule from Workshop 6 (visible, editing). Name the callback explicitly.

Step 3/Wrapping

Provider order

import { AuthProvider } from "./context/AuthContext.jsx";

<StrictMode>
  <BrowserRouter>
    <AuthProvider>
      <App />
    </AuthProvider>
  </BrowserRouter>
</StrictMode>

AuthProvider goes inside BrowserRouter, because things it renders will want to navigate. The other way round works today and breaks the moment the provider needs useNavigate.

The general rule: a provider can use anything wrapping it, and nothing it wraps. Nesting order is a dependency order.

Step 3/When to use it

When to use Context

  • Use it for genuinely app-wide values: the logged-in user, a theme, a language.
  • Don't use it for a value one component passes to its own child. That's a prop, and props are easier to follow.
  • Every component reading a context re-renders whenever that context's value changes. Put too much in one and you re-render the app on every keystroke.

Notice what we did not move into context: the professionals list. It's used by one page. It stays exactly where it is.

Say this now, because the next thing an excited student does is put all their state in a context and wonder why the app feels slow.

Step 4/Solution

The submit handler

const { login } = useAuth();
const navigate = useNavigate();

async function handleSubmit(e) {
  e.preventDefault();
  setError(null);
  setSubmitting(true);

  try {
    const res = await axios.post(`${API_BASE}/login`, form);

    login(res.data.token);              // remember who we are
    navigate("/", { replace: true });   // then go somewhere
  } catch (err) {
    if (err.response) {
      setError(err.response.data.message);
    } else {
      setError("Could not reach the server. Is the backend running?");
    }
  } finally {
    setSubmitting(false);
  }
}

replace: true swaps the history entry instead of adding one, so pressing Back from the list doesn't return them to the login form they just used.

Step 6/Solution

Fill in components/ProtectedRoute.jsx

import { Navigate } from "react-router";
import { useAuth } from "../context/AuthContext";

function ProtectedRoute({ children }) {
  const { isLoggedIn } = useAuth();

  if (!isLoggedIn) {
    return <Navigate to="/login" replace />;
  }

  return children;
}

export default ProtectedRoute;

replace again, for a sharper reason: without it the blocked URL stays in the history, so pressing Back sends them into the redirect again. They'd be stuck.

Step 6/Logout

Logging out

function handleLogout() {
  logout();              // clears context AND localStorage
  navigate("/login");    // then move them somewhere they're allowed to be
}

Order matters and not for the reason people expect: clearing the token re-renders ProtectedRoute, which would redirect anyway. The explicit navigate is about being clear, not about being necessary.

Check localStorage in DevTools before and after. Logging out has to remove the token, not just forget it in React — otherwise a refresh logs you back in.

The DevTools check is worth doing live. "It works until you refresh" is the classic half-done logout, and they'll write it at some point.

Recap

What you built, and one thing it doesn't do.

Six minutes. The second slide of this step matters more than the first.

Step 7/The shape

What you built

URL → Route → Page → useAuth() → render or redirect

  • Routing decides which screen. The address bar is the state.
  • Context decides what every screen knows. One value, no prop drilling.
  • The API decides whether the token is real. React only stores it.

Ask someone to trace what happens when you type / into the address bar while logged out. If they can walk the arrow, the session worked.

Step 7/Not security

What this does not protect

  • The API is exactly as open as it was this morning. Nothing on the server checks the token — nothing even asks for it.
  • Anyone can still curl -X DELETE http://localhost:5000/api/professionals/<id> and it will work.
  • The token in localStorage can be typed in by hand. localStorage.setItem("token", "anything") and our guard is satisfied.

Route guards are a user experience feature: don't show people a page they can't use. Security happens on the server, and that's the next workshop — the JWT the backend has been signing since Workshop 5 finally gets verified.

Do not soften this. A student who thinks a client-side route guard is authentication will ship that belief. Demonstrate the fake token if there's time — it takes fifteen seconds and it lands hard.
