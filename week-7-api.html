Step 1/The shift

The component stops being the source of truth

Until today

State holds the list. The component owns the data. Refresh and it's gone.

From today

The database holds the list. The component asks for the data and displays it.

component  →  HTTP request  →  Express  →  Mongoose  →  MongoDB
                                                            ↓
component  ←    response     ←  Express  ←  Mongoose  ←  MongoDB

The cost of that round trip: everything becomes asynchronous. That's what the next slide is for.

Draw this on the board rather than relying on the slide. Students refer back to a board diagram all session; they don't scroll back through slides.

Step 1/async & await

The three keywords

async function loadData() {
  try {
    const res = await axios.get(url);   // await = wait for the answer
    console.log(res.data);
  } catch (error) {
    // runs only if it failed
  } finally {
    // runs either way — this is where loading gets switched off
  }
}
  • async marks a function that is allowed to wait.
  • await pauses until the answer arrives — only legal inside async.
  • finally runs whether it worked or not.

Don't teach .then() chains today. If someone asks, say it's the same thing written differently and move on.

finally looks pointless right now. Flag that it earns its place in Step 4.

Step 02

axios

The HTTP client we'll use for every request today.

Slide only — nobody writes fetch today. The point is that they recognise it when a tutorial uses it.

Step 2/What it is

An HTTP client for JavaScript

  • A library for sending HTTP requests and reading the responses — installed with npm install axios.
  • Promise-based, so it works directly with the async / await syntax from Step 1.
  • Runs in the browser and in Node. The same API on both sides.
  • It is not part of React. Nothing about it is React-specific — it's the standard way JavaScript applications talk to an API.
import axios from "axios";

const res = await axios.get("http://localhost:5000/api/professionals");

console.log(res.data);      // the JSON the server sent back
console.log(res.status);    // 200

The response object holds more than the data — res.data is the body, res.status is the HTTP status code.

The res.data vs res distinction catches people immediately. They will write setProfessionals(res) at least once and render an object.

Step 2/fetch vs axios

The same request, twice

fetch — built into the browser
const res = await fetch(url);

if (!res.ok) {
  throw new Error(res.status);
}

const data = await res.json();
axios — one npm install
const res = await axios.get(url);

const data = res.data;
  • It parses JSON for you. No res.json().
  • It throws on 404 and 500. fetch resolves happily on an error page.
  • It sets JSON headers on POST automatically.

Reason two is the one that matters. With fetch, a 404 sails past your catch, then res.json() tries to parse an HTML error page and you get Unexpected token '<' — an error that tells you nothing about what actually went wrong.

Say plainly: fetch isn't worse, it's lower level. Same idea, two extra lines.

Step 2/The methods

One method per CRUD operation

// READ    — GET /api/professionals
const res = await axios.get(API_URL);

// CREATE  — POST /api/professionals        (data in the body)
await axios.post(API_URL, values);

// UPDATE  — PUT /api/professionals/:id     (id in the URL, data in the body)
await axios.put(`${API_URL}/${id}`, values);

// DELETE  — DELETE /api/professionals/:id  (id in the URL, no body)
await axios.delete(`${API_URL}/${id}`);

The method name is the HTTP verb. These four lines are every request you will write today — the rest of the session is deciding where to put them.

Leave this slide up while they work. It's the reference sheet for both tasks, and it saves the same question being asked four times.

Point out the pattern: anything that targets one record puts the id in the URL; anything that sends data puts it in the second argument.

Step 3/useEffect

The useEffect hook

  • A React hook for side effects — work that isn't part of building the JSX, like fetching data from an API.
  • The effect runs after React has rendered and put the screen up — never during.
  • The second argument controls how often it runs. That's the next slide.
useEffect(() => {
  // the side effect — runs after the render
}, [dependencies]);

Fetching is the textbook example: a request takes time, and React cannot pause a render to wait for it.

Frame it as "the escape hatch for anything that isn't rendering", not as "the data-fetching hook". They'll meet timers, subscriptions and event listeners in the same place later.

If someone asks why they can't just call axios in the component body: it would fire on every single render, and setState causes a render.

Step 3/Dependencies

The second argument decides how often it runs

Written asThe effect runs
useEffect(fn)After every render — almost never what you want
useEffect(fn, [])Once, after the first render — what we need today
useEffect(fn, [query])After the first render, and again whenever query changes

We want the list loaded once, when the page opens. That's the empty array.

The third row is worth naming even though we don't use it — it's how searching against the server would work, and it stops [] looking like magic punctuation.

The first row is the infinite loop: the effect sets state, state causes a render, the render runs the effect again.

Step 3/Say this first

Three rules before writing an effect

  • The effect callback cannot be async. useEffect(async () => ...) returns a promise where React expects a cleanup function. So we declare an inner function and call it.
  • [] at the end means "once, on mount". Leave it off and setState triggers a render, which reruns the effect, which fetches again — forever.
  • StrictMode runs effects twice in development. The Network tab will show two requests. Intentional, dev-only, gone in the production build.

Each of these costs ten minutes of confusion if you say it afterwards instead of now. The double-request one especially. If you don't pre-empt it, the first person to open the Network tab derails the room with "I think I wrote an infinite loop."

Optional 10-second demo: remove the [], watch the request counter spin, put it back.

Step 3/The effect

Fetch on mount

import { useState, useEffect } from "react";
import axios from "axios";

const API_URL = "http://localhost:5000/api/professionals";

async function loadProfessionals() {
  const res = await axios.get(API_URL);
  setProfessionals(res.data);
}

useEffect(() => {
  loadProfessionals();
}, []);

loadProfessionals lives outside the effect on purpose — delete, add and edit all need to call it later.

ESLint may warn that loadProfessionals is a missing dependency. Say it's intentional — we want this on mount only. Do not open useCallback today.

Putting the function outside the effect now saves rewriting it twice in Steps 5 and 6.

Step 3/Same-origin policy

A browser rule, not a server error

  • A page served from localhost:5173 may not read a response from localhost:5000.
  • Different port = different origin. So does a different host or protocol.
  • The server must opt in by sending Access-Control-Allow-Origin.

This is enforced by the browser, and only the browser. curl, Postman and the backend's own test suite don't care — which is exactly why npm test passes while the app is broken.

The "why does Postman work?" question comes up every time. Answer it before it's asked — it's the cleanest way to make same-origin concrete.

One line on the purpose: it stops a random site reading your logged-in bank account's API responses.

Step 3/The fix

Two lines — in the backend

// server.js
const cors = require("cors");

app.use(cors());     // allow every origin — fine for learning

Restart the backend, refresh the browser. The list appears.

In production you'd name the allowed site instead: app.use(cors({ origin: "https://yoursite.com" })). Allowing everything is a learning convenience.

FixedThe list loads from MongoDB

Point out that the fix was in the other project. The bug appeared in React and was solved in Express — that's the lesson about knowing which side you're on.

Step 3/What just happened

Effects run after paint, not during render

  1. Component renders with professionals = [] — the page is empty.
  2. The effect runs, after that render is on screen.
  3. The request goes out. The user is looking at an empty list.
  4. The response arrives → setProfessionals(res.data).
  5. State changed, so React renders again — this time with data.

There is always a moment where the page is rendered and the data isn't there yet. That's what Step 4 is about.

App works nowThe list loads from the database

Step 4/Four states

Every request has four outcomes

const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

async function loadProfessionals() {
  try {
    const res = await axios.get(API_URL);
    setProfessionals(res.data);
    setError(null);
  } catch (err) {
    setError("Could not load. Is the server running?");
  } finally {
    setLoading(false);        // runs either way
  }
}

axios throws on 404 and 500, so catch actually catches. That's reason two from Step 2 paying off.

This is where finally earns its place — loading must stop whether the request worked or not, and you'd otherwise write setLoading(false) twice.

Step 4/Render them

Loading · error · empty · success

if (loading) return <p>Loading…</p>;
if (error) return <p className="form-error">{error}</p>;

// the empty state you already wrote in Workshop 6 still handles the third
// {visible.length === 0 ? <p>No professionals found</p> : ...}

Trigger it live: stop the backend, refresh the browser. The error state appears. Start it again, refresh, the list comes back.

Students write only the success path. Making the failure happen on demand is the whole point of this step.

Step 5/The pattern

Where does the screen get its new state?

Re-fetch — what we're doing

Send the change, then ask the server for the list again. Simple, always correct, one extra request.

Update local state

Change React's copy to match what you think the server did. Faster, no extra request, and wrong the moment your guess differs from reality.

Every mutation from here is the same two steps: send the change → re-read the list. POST and PUT are this exact shape.

Name option two as "optimistic updates" so they have the term, then move on. It's a Workshop 8+ topic and it opens a rollback discussion you don't have time for.

Step 6/What left the file

Three things to notice

  • crypto.randomUUID() is gone. MongoDB generates _id now. Ids were never really ours to invent.
  • .map() and .filter() have both left App. Ask what replaced the entire immutability toolkit you spent Workshop 6 learning.
  • key={editingId ?? "new"} is untouched. The remount trick had nothing to do with where the data lived.

The answer to the second one: the server, plus a re-fetch. Immutability still matters — it just moved to a place you can't see from here.

Don't skip the second bullet. Watching a technique they just learned become unnecessary is unsettling unless you explain why it still mattered.

Step 7/Still missing

Known limitations

  • No loading state on the buttons. Delete something on a slow connection and nothing happens for a second.
  • Search still filters locally. Asking the server on every keystroke would be wasteful — that's debouncing.
  • The API has no lock on it. Anyone who knows the URL can delete everything.

That last one is next workshop. The backend already issues a JWT at login — nothing is checking it yet.

Ending on the limitations rather than a victory lap sets up the next session and stops them thinking this is production-ready.
