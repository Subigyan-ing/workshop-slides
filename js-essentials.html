  • (prev) => — an arrow function.

Concept 1 of 5

Arrow functions

A shorter way to write a function. Same thing, fewer words.

Arrows/The shape

The same function, written three ways.

// 1 — the long way
function double(n) {
  return n * 2;
}

// 2 — an arrow, with a body
const double = (n) => {
  return n * 2;
};

// 3 — an arrow, no braces, no return
const double = (n) => n * 2;

All three are the same function. double(4) gives 8 every time.

Stress that this is a spelling change, not a new capability. The only real behavioural difference — this binding — never comes up in these tasks.

Arrows/Implicit return

Braces mean "I will write return myself."

With braces — you must return
const f = (n) => {
  return n * 2;
};

f(4)  // 8
Braces, but no return
const f = (n) => {
  n * 2;
};

f(4)  // undefined

A block { } is a list of instructions. It does not hand anything back unless you say return. Drop the braces and the single expression is the return value.

Common bugBraces added, return forgotten — the function quietly returns undefined
Arrows/When it is allowed

One expression, no braces. That is the whole rule.

const double  = (n) => n * 2;
const isAdult = (p) => p.age >= 18;
const name    = (p) => p.first + " " + p.last;

// two statements — braces and return are required
const shout = (s) => {
  const trimmed = s.trim();
  return trimmed.toUpperCase();
};

If you need a second line, you need braces. If one expression says it all, drop them.

Arrows/The parenthesis trap

To return an object, wrap it in parentheses.

Reads as a code block
(p) => { name: p.name }

// returns undefined
Reads as an object
(p) => ({ name: p.name })

// returns { name: "Ada" }

JavaScript sees { after the arrow and assumes you are opening a function body. The parentheses say "no — this is a value". This is exactly why the form solution reads setForm((prev) => ({ ...prev })) and not => { ...prev }.

RememberArrow, then an object → you need => ({ })

This one catches almost everybody in Task 7. If a student's form silently stops updating, this is the first line to look at.

Arrows/In the tasks

Where arrows show up in Week 6–7.

// inside .filter — one expression, no braces
professionals.filter((p) => p.id !== id)

// inside .map — returns JSX
professionals.map((p) => <Card key={p.id} professional={p} />)

// as an event handler written inline
<button onClick={() => onDelete(p.id)}>Delete</button>

() => with empty parentheses is a function that takes no arguments. Inline handlers use it to delay the call — onDelete(p.id) alone would run immediately.

Concept 2 of 5

Square brackets
on objects

For when you don't know the key until the code runs.

Object keys/Reading a value

Two ways to read the same field.

const person = { name: "Ada", title: "Engineer" };

person.name       // "Ada"  — dot: you type the key
person["name"]    // "Ada"  — brackets: you pass a string

const field = "name";
person[field]     // "Ada"  — the string came from a variable
person.field      // undefined — looks for a key called "field"

Dot notation takes the word you literally typed. Brackets take whatever the expression inside evaluates to, then use that as the key.

Object keys/Writing a value

Brackets work when building an object too.

Key is the literal word
const field = "title";

{ field: "Engineer" }

// { field: "Engineer" }
Key is worked out first
const field = "title";

{ [field]: "Engineer" }

// { title: "Engineer" }

Same rule, mirrored. Without brackets you get a key spelled field. With them you get whatever field holds.

Object keys/The real line

One handler for every input.

<input name="name"  value={form.name}  onChange={handleChange} />
<input name="title" value={form.title} onChange={handleChange} />

function handleChange(e) {
  setForm((prev) => ({ ...prev, [e.target.name]: e.target.value }));
}

Type in the title box and e.target.name is "title", so [e.target.name] becomes the key title. One function, any number of fields — that is what the brackets buy you.

PayoffAdd a fourth input and the handler needs no change

Without computed keys you would need handleNameChange, handleTitleChange, and so on. Worth saying out loud — the brackets are what collapse four handlers into one.

Concept 3 of 5

The spread
operator ...

"Unpack everything that was in there, into here."

Spread/Arrays

Copy the old items in, then add yours.

const nums = [1, 2, 3];

[...nums]         // [1, 2, 3]        a copy
[...nums, 4]      // [1, 2, 3, 4]     copy, then append
[0, ...nums]      // [0, 1, 2, 3]     prepend, then copy

nums              // [1, 2, 3]  — untouched, every time

Every one of these builds a new array. The original is never modified — that last line is the point.

Spread/Objects

Same idea. Later keys win.

const person = { name: "Ada", title: "Engineer", age: 36 };

{ ...person }                  // an identical copy
{ ...person, title: "Lead" }   // copy, then overwrite title
{ title: "Lead", ...person }   // copy wins — title is "Engineer"

Order decides the winner. Put your change after the spread or the old value overwrites it — a bug that looks like "my update did nothing".

Order mattersYour change goes after the ... not before
Spread/Why not just push

React looks for a new object, not a changed one.

Changes the old array
list.push(item);
setList(list);

// same array →
// React sees no change →
// nothing re-renders
Builds a new array
setList([...list, item]);



// new array →
// React re-renders

React compares the old value to the new one by identity. Mutating in place leaves it holding the same thing it already had, so it concludes nothing happened.

The push version is the single most common "my code is right but the screen won't update" bug in these tasks. Same applies to sort and splice — both mutate.

Spread/The real line

Two spreads, one statement.

setProfessionals((prev) => [
  ...prev,
  { ...values, id: crypto.randomUUID() },
]);
  • ...prev — every professional already in the list.
  • ...values — every field the form collected.
  • id: after the spread, so it is added to the copy.

An array spread and an object spread doing the same job at two levels: copy what was there, add what is new, change nothing in place.

Concept 4 of 5

setState
(prev) =>

Asking React for the current value instead of guessing it.

prev/The two forms

Pass a value, or pass a function.

const [count, setCount] = useState(0);

// a value — "make it this"
setCount(5);

// a function — "take what it is, give me what it becomes"
setCount((prev) => prev + 1);

prev is just a parameter name — React fills it in with the current value when it runs your function. (c) => c + 1 works identically.

prev/The stale value

Setting state does not change the variable you are holding.

Reads a frozen count
setCount(count + 1);
setCount(count + 1);

// count was 0 for both
// result: 1
Reads the live count
setCount((p) => p + 1);
setCount((p) => p + 1);


// result: 2

During one render count is a fixed number — it does not update mid-function. The updater form runs later, when React knows the real value.

Stale stateTwo updates in a row, only one lands

If someone doubts it, have them add two setCount calls to the counter task and watch it go up by one.

prev/When to use which

Does the new value depend on the old one?

  • Yes → use the function.Adding to a list, toggling a boolean, counting, editing one field of a form.
  • No → pass the value.Resetting a form, storing what someone typed, setting an id you already have.
setOpen((prev) => !prev);                    // depends on old
setList((prev) => prev.filter((p) => p.id !== id));  // depends on old
setForm(EMPTY_FORM);                          // does not
setQuery(e.target.value);                     // does not
Concept 5 of 5

HTML that is
actually JSX

It looks like the markup you know. A few words changed.

JSX/What changed

Four differences you will hit immediately.

HTML JSX Why
class className class is a reserved word in JavaScript
for htmlFor so is for
onclick onClick events are camelCase, and take a function not a string
<br> <br /> every tag must be closed

Curly braces mean "JavaScript goes here": className="btn" is a string, onClick={handle} is a value.

JSX/What e holds

Every handler is handed an event.

<input name="title" onChange={handleChange} />

function handleChange(e) {
  e.target          // the input element itself
  e.target.name     // "title"  — its name attribute
  e.target.value    // what is currently typed in it
}

e is just the parameter name — React passes the event in whether you name it e, event or anything else. e.target is always the element the event came from.

JSX/preventDefault

A form's default job is to reload the page.

function handleSubmit(e) {
  e.preventDefault();
  onSubmit(form);
}

<form onSubmit={handleSubmit}>

Without that first line the browser submits the form the old-fashioned way: full page reload, every piece of state gone, your handler's work thrown away. It looks like a crash. It is a page refresh.

SymptomThe page flashes and the list empties itself

Also worth flagging: a bare button inside a form defaults to type="submit". That is why the deck writes type="button" on Delete and Edit.

JSX/value + onChange

React holds the text. The input just displays it.

<input
  name="title"
  value={form.title}      // state decides what is shown
  onChange={handleChange} // typing asks state to change
/>

The pair is the point. value without onChange gives you a box you cannot type in — the state never changes, so the displayed value never does either.
